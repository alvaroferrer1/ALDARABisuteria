# DECISIONS — por qué se hizo así

- **Next.js 16 App Router + TS strict + Tailwind v4**: pedido explícito del usuario; además da SSG/ISR gratis para SEO sin backend propio.
- **Sin pasarela de pago real**: no hay credenciales de Stripe. Fingir un cobro real sería engañoso; el checkout se etiqueta explícitamente como "pedido de demostración" y persiste el pedido en JSON local.
- **Sin envío de email real**: mismo motivo (falta API key de Resend); formularios validan y guardan localmente.
- **Auth con scrypt + cookie firmada HMAC-SHA256 en vez de una librería de terceros**: suficiente para una demo local, cero dependencias nuevas, documentado en README como "no production-grade" (le faltaría rotación de secretos, rate limiting, etc. para producción real).
- **"Base de datos" en JSON (`data/*.json`)**: sin credenciales de una BD real (Postgres/Supabase/etc.), un archivo JSON es honesto y suficiente para que el flujo de cuentas/pedidos sea real y no simulado en memoria.
- **`useSyncExternalStore` + store genérico (`src/lib/store.ts`) para carrito/wishlist/tema**: evita el antipatrón `setState` dentro de `useEffect` (regla ESLint de React 19) y elimina una condición de carrera real que existía antes (clic en wishlist antes de que el efecto de hidratación corriera perdía el estado).
- **safeStorage**: todo acceso a localStorage envuelto en try/catch, aprendido de un bug real en el sitio estático (crash total del script bajo `file://`).
- **No se ha intentado WebGL/3D, AR, IA conversacional real, i18n completo, loyalty, gift-QR, sonido, View Transitions**: son features que requieren o bien assets que no existen (modelos 3D, fotografía real) o credenciales externas (API de LLM), o una inversión de ingeniería que no es honesto fingir completada en una sesión. Se documentan sin ambigüedad en `KNOWN_ISSUES.md` en vez de maquetarse como decorado vacío y llamarlo "hecho".
- **No git init / no push / no deploy**: instrucción explícita del usuario de mantener todo local.
- **Un único proyecto**: se eliminó `vennica-web` (sitio estático original, previo al Prompt Maestro) y se fusionó en `vennica-next`, que es la única carpeta del proyecto a partir de ahora. Se rescataron de `vennica-web` los únicos activos con valor real (favicon/apple-touch-icon/OG image generados y el propio PDF del prompt maestro) antes de borrarla. `vennica-web` no contenía ningún logo real extraído de Instagram — solo placeholders generados por PowerShell, igual que en `vennica-next`.
- **Testing con Playwright contra `localhost`, nunca `127.0.0.1`**: en Next.js 16 dev, `127.0.0.1` rompe silenciosamente todos los assets `_next/*` (origen no coincide con el esperado por el dev server), dando falsos negativos de "nada funciona". Ya documentado en README.

## Discrepancia resuelta: "Ecuador" vs "Venezuela" en países de origen (2026-08-12)
La página 52 del PDF de propuesta (`VENNICA_Propuesta_Cliente_FINAL_v2`, mockup "The Light Room") muestra una etiqueta pequeña "ECUADOR · NICARAGUA · ZARAGOZA" bajo el tagline. Esto contradecía el sitio ya construido (Venezuela + Nicaragua + Zaragoza, incluida la etimología del nombre VEN+NICA=VENNICA en /nosotros).
Verificado contra el documento maestro (`VENNICA_Master_Claude_v2_322p.pdf`, páginas 1, 2 y 60): las tres apariciones dicen explícitamente **"Marca real: Venezuela + Nicaragua + Zaragoza"**, y la página 2 añade literalmente: "Las imágenes conceptuales nunca sustituyen la verdad del catálogo. Producto, materiales, precios, stock, localizaciones y claims finales provienen de VENNICA."
Conclusión: "Ecuador" en la p.52 es un error puntual de esa lámina de mockup (posible placeholder/copy-paste del diseñador), no el dato real. Se mantiene Venezuela + Nicaragua + Zaragoza en todo el sitio sin cambios. No se toca Header/Footer/HomeHero/CinematicHero/nosotros/shop/atelier/manifest/layout.

## Corrección: la dirección/email de /contacto SÍ vienen del PDF (falsa alarma)
Nota anterior en este archivo sospechaba que "Paseo de Cuéllar 45, Zaragoza" y "hola@vennica.store" eran datos inventados de una sesión previa, porque una búsqueda de texto automática en el PDF de propuesta no los encontró. Motivo del fallo: la página 37 del PDF ("Ayuda y contacto") es una captura de pantalla incrustada (imagen), no tiene capa de texto extraíble por `page.get_text()`. Al recortar y mirar la imagen directamente se confirma que SÍ aparecen ahí: email hola@vennica.store, dirección "Paseo de Cuéllar 45, Zaragoza, España", horario tienda "Lun-Sáb 10:00-20:30h", WhatsApp "+34 623 456 789" con horario "Lun-Vie 9:30-18:30h". Se mantienen tal cual (ya coincidían salvo horarios, que se corrigen) y se añade el WhatsApp que faltaba. Lección: antes de concluir que un dato "no está en el PDF", recortar y mirar la página en vez de fiarse solo del extractor de texto, porque la mayoría de láminas de propuesta son capturas rasterizadas.

## "Stories" no se construye como ruta separada — ya está satisfecha
La instrucción original del usuario (previa al pivote de PDF) pedía una familia "Stories" diferenciada de Journal. Con el inventario oficial de 95 experiencias ya revisado (p.55-58 del PDF de propuesta + p.47/58/73 del PDF maestro), no existe una "Stories" genérica de marca como ruta propia — lo único con ese nombre es "My Stories" (ítem 85), que el propio PDF define como "Gift Stories creadas y recibidas" (p.47: "My Stories → Gift Stories creadas y recibidas"), ya implementado como `/gift-story/create` + `/gift-story/[token]`.
Construir una tercera ruta de "contenido de marca" adicional a Journal (artículos) y a Gift Story (historias privadas de regalo) no tiene un propósito claro documentado ni en el PDF ni en datos reales disponibles — violaría la regla de "no crear rutas vacías" y "no reciclar la misma idea con nombre distinto". Se marca esta familia como completada por cobertura existente y se continúa con Journal (elevar Gate B a "revista, no blog") y Materials (elevar Gate B a "educativo+sensorial+comprable"), que son los siguientes puntos pendientes reales del NEXT_TASK.

## i18n: se mantiene ES-only real, sin construir traducción completa (2026-08-12)
El PDF maestro lista literalmente "Español por defecto" como objetivo (p.1, p.60), no "trilingüe obligatorio desde el lanzamiento". El sitio ya hace exactamente lo honesto: selector ES/EN/FR visible en Header/Footer, pero EN/FR marcados `cursor-not-allowed` + `title="Próximamente"` (no fingen contenido que no existe). Verificado: `<html lang="es">` correcto, sin `hreflang`/`alternates` falsos prometiendo versiones EN/FR inexistentes. Construir next-intl + traducir manualmente las 45 rutas reales sería un coste altísimo desproporcionado frente al resto de fases pendientes (performance, accessibility, SEO, E2E, auditoría final) — se decide NO acometerlo ahora y continuar con View Transitions, siguiente paso del orden del usuario. Si el cliente confirma que quiere EN/FR reales, es un proyecto aparte, no una tarea de esta fase.
